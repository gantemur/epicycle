# Phase 4A workspace architecture

Phase 4A adds a pure TypeScript state foundation. The accepted Phase 3C interface still uses `app.ts` and `state.ts`; no workspace controls or new renderer are active yet.

## Three boundaries

- **Clock:** `WorkspaceState.clock.ut1Jd` is the one authoritative, assumed UT1 astronomical Julian Day. Playing, speed, and direction also belong to this one clock. One future animation loop will call `tickClock`; no display owns a clock. `jumpToToday` takes an explicit UTC millisecond value through the existing UTC-to-assumed-UT1 boundary; the UI must label that approximation. Historical example jumps and steps set this same instant.
- **Historical model:** Versioned JSON parameter records remain authoritative. `model-registry.ts` declares each implemented model's body, source identity, source and validation status, dependencies, supported observables and their native frame labels, geometric view centres, and explicit policy domains. Evaluators use `modelDaysAtUt1` to convert the shared instant to the Ptolemaic Alexandria local day or the Copernican Frauenburg local day. Alexandria 30° E remains provisional; Frauenburg 19°40′ E is documented. Neither local day is a modern TT timestamp.
- **Display:** A serializable, version 1 discriminated union has `geometry` and `time-series` configurations. A geometry panel selects one body/model/policy/centre plus trail, circles, construction lines and annotations. A plot selects its own trace list, window, longitude wrapping, axis labels, optional follow flag, frame declaration and analysis mode. `startUt1` and `endUt1` alone define its window; pan and zoom transform those endpoints rather than storing competing offsets or scale. The follow flag tells a future controller to shift the endpoints deliberately. The plot's window never changes the current clock instant; its current-time marker reads `clock.ut1Jd` directly. Moving a marker alone does not require resampling unchanged curves.

The existing single-model Ptolemaic `state.day` and comparison `state.compareUt1` remain untouched in the live UI. Both state layers read the same fixture-derived Nabonassar example from `historical-examples.ts`; the legacy `state.ts` export remains for current consumers. `ptolemyDayToAssumedUt1` is the explicit inverse of the current provisional Alexandria conversion, tested with the legacy day convention. Phase 4B can migrate the live controls through this boundary without changing Nabonassar examples or treating local day counts as identical.

## Validation and availability

`validateDisplay` checks mathematical model/body, observable, view centre, policy, plot settings, trace IDs, and frame conditions. Renderer availability is a separate registry field. Ptolemy has only an Earth-centred mathematical and rendered geometry capability; a physical true-Sun Ptolemaic view is unsupported. Copernicus has Earth and true-Sun-centred mathematical geometry, but only an Earth-centred renderer at present. A true-Sun configuration is mathematically valid and reports `renderer-unavailable` until its renderer and labels exist; it must not be offered as a working UI choice before then.

The source-limited Copernican `sn-local-uniform-1473-1523` policy uses the existing 1473–1523 guard. `sn-uniform-exploratory` is a separately selected continuation, never an automatic fallback. `displayAvailabilityAt` describes the current-time marker/readout, including a partial result when only some plot traces are available there. Independently, `traceCoverage` describes full, partial, or no coverage of the plot's historical window. Thus a plot entirely within 1512 remains usable when the global clock is in 2026, even though its Copernican marker is unavailable. Phase 4B must draw window gaps with an explanation and suppress unavailable marker values. A failed panel cannot stop the clock or other panels. The wider JD 1,200,000–3,000,000 boundary is numerical only, not a historical validity claim.

Plot `overlay` means displaying selected traces together, including future different bodies. Each trace's native frame is available through its model registry entry and `nativeFrameForTrace`; a native overlay must label these frames separately and must not treat unlike frames as aligned. `model-disagreement` requires two different models of the same body and observable, with a common native frame or an explicit **nominal historical tropical alignment**. That alignment is not a calibrated modern frame. Cross-body angular separation is a different mathematical operation; observational error requires a calibrated reference and matching metadata. Neither is implemented or silently inferred from an overlay. The reconstructed Copernican Mars apogee remains tied to its selected policy and restricted source domain.

## Panel and preset behavior

`workspace-state.ts` supplies pure add, remove, collapse, reorder, replace-settings, window-transform, clock, and preset operations. Added and updated panels copy their nested trail, window, trace, and analysis settings, including when a preset draft is reused. IDs are monotonic (`panel-1`, etc.) and stable through ordering/removal. Up to four panels are active, including collapsed ones; an empty workspace is valid and needs an eventual Add Display control. A plot initially allows up to four traces as a UI limit, not a limit on future historical models. The same model can appear in several panels with independent settings. `restoreWorkspace` validates version, configuration, panel IDs, and the next-ID counter, copies the panels, and forces `playing: false`; invalid saved data is rejected. It does not read browser storage, and persistence is not enabled yet.

Presets are Explore one model, Compare longitudes, Desktop explore, and Detailed comparison. The suggested desktop start is a longitude plot plus one Ptolemaic construction; the suggested phone start is the plot alone. Suggestions apply only when creating a new workspace. Resizing an existing workspace changes presentation only and must not call `applyWorkspacePreset` or discard panels.

## Phase 4B migration contract

1. Keep the current `app.ts` experience available while first mounting a managed geometry panel and plot using the existing `diagram.ts`, `copernicus-diagram.ts`, and comparison plotting/evaluation modules. Introduce a single workspace controller; do not run an additional animation loop.
2. Map the accepted Single Ptolemy Nabonassar view through `ptolemyDayToAssumedUt1`, and map Compare through its existing `compareUt1`. Verify example dates, longitudes, and playback before removing the legacy parallel time fields. Preserve the current English/Mongolian strings and source warnings.
3. Move the current plot range and display selections into per-panel configuration. Reuse its existing sampling cache so a clock-marker move alone does not resample; implement window following deliberately, with sampling only when the effective range changes. Mark source-policy gaps rather than extending curves.
4. Add a compact global playback control, panel add/remove/collapse/reorder/settings, and a clear empty-workspace action. A geometry tap-to-play handler should live on a stable diagram container, excluding controls and labels, not on regenerated SVG children or the whole panel. Preserve phone access to playback while a plot is visible. Add a larger panel view only where useful; drag-and-drop is optional later.
5. Implement and label true-Sun Copernican rendering separately before exposing its capability in visible controls. Keep the Ptolemaic view Earth-centred. Browser persistence/shareable URLs and new observables remain later work.

Future latitude, additional bodies, and historical variants add new sourced evaluators and capability entries, then the relevant display/evaluation support. A model ID in a panel refers to a registry record rather than copying parameters. A synthetic Saturn capability appears in unit tests solely to demonstrate validation rules; it is not an implemented astronomical model or UI choice. Future sky-path, numerical readout, and diagnostics display types can extend the union after their scientific and rendering contracts are defined.
