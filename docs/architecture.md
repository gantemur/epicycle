# Architecture

## Scientific-code readability contract

All maintained Python and TypeScript numerical algorithms must use clear quantity names and explicit steps. Explain nontrivial formulas, sign conventions, units, reference frames, epochs, and historical assumptions with comments or docstrings; put exact source locators in the mathematical specification and near delicate implementation steps when useful. Comments explain why a formula is used, not what an obvious assignment does. Keep historical definitions, numerical evaluation, chronology, interaction state, rendering, and plot sampling separate. Prefer a straightforward expression to a clever compressed one.

Tests and generated fixtures must expose provenance and remain reviewable by a person. Verifiability and readability outrank marginal performance. Optimize only for an identified bottleneck while preserving a simple, testable reference formulation. Maintained source, including CSS, must not be unnecessarily compressed or minified; production bundles may be minified.

## Boundaries

1. **Historical definitions:** versioned, reviewable data per `(tradition, work, variant, body)`. Each parameter stores the original sexagesimal string or tuple, normalized value and unit, epoch, frame, source ID with book/chapter/page/table, and one of `explicit`, `derived`, `reconstruction`, `modern_fit`. Add ambiguity notes and alternate readings. A missing value means unknown, not zero. A model record states which observables are actually defined.
2. **Historical evaluator:** pure functions of a model definition and an explicit time argument. Return geocentric coordinates *and* intermediate construction points, angles, and distances with units; rendering consumes these results. Keep any original geometrical lengths distinct from screen pixels.
3. **Chronology and coordinates:** one documented Julian-day representation plus explicit civil calendar (proleptic Julian or Gregorian), astronomical year numbering and BCE display conversion, day boundary, time scale, equinox/ecliptic, obliquity, precession, and angular wrapping rules. Convert at defined boundaries rather than inside individual models. Record uncertainty in ancient ΔT.
4. **Modern reference:** a separate adapter reporting dataset and version, coverage, frame, correction choices, and whether coordinates are geometric or apparent. The browser may use pre-generated, validated coefficients; Python may use a local JPL kernel. Generation-time download is acceptable; deployed evaluation should work offline.
5. **Presentation:** a browser application that evaluates at most two historical models and optional modern reference. Two synchronized geometry panels avoid mixing unlike constructions. Geocentric longitude is the initial shared observable. A Sun-centred view must label original geometry, coordinate re-centring, or an assumption-dependent reconstruction separately; a geocentric construction does not uniquely determine a physical heliocentric orbit.
6. **Research:** independent Python commands for historical evaluation, table checks, reference comparisons, optimization, sensitivity work, and reproducible paper tables/figures. Scientific scripts and configurations are versioned. Large kernels remain external with acquisition instructions and checksums.
7. **Provenance and validation:** per-parameter source locators, typed fixtures, independent historical table examples, numerical cross-checks across Python/browser, and explicit validation status. `implemented`, `source-checked`, and `numerically-validated` are separate states.

## Initial technology choices

- Browser: TypeScript, Vite, native SVG/Canvas as appropriate, and small reusable UI modules. Use a centralized `en`/`mn` message catalogue and a compact **English | Монгол** header toggle, with local selection persistence. Avoid a heavy internationalization or chart library until the actual plotting needs justify one. Vite's base path must be `/epicycle/` when deployment is authorized.
- Layout: phone-first at 360–390 CSS px; a large geometry panel, touch-sized controls, stacked or collapsible sections, and comparison tabs on narrow screens. Respect reduced motion; do not encode meaning only in colour. Translate graph labels, units, legends, tooltips, errors, model names, and source information.
- Python: a small package with standard-library historical mathematics first; add NumPy/SciPy, plotting, and JPL tooling only to the research extras that need them. Pin versions when reproducible experiments begin. Use a local JPL ephemeris interface exposing general position vectors rather than CALTIB's lunar-elongation-specific facade.
- Shared data: human-readable JSON with schema validation, sourced sexagesimal values, and versioned expected-output fixtures. Both runtimes parse the same definitions; neither browser code nor SOL constants are the canonical source. Decide the exact schema only after the first source-verified Mars transcription.

## Phase 2 implementation boundary

`data/mars-almagest-v1.json` remains the single historical parameter record. `web/src/model.ts` imports it and independently evaluates the Cartesian construction; it returns the Earth, deferent centre, equant, epicycle centre, Mars, radii, angles, and distances in historical units. `web/src/diagram.ts` maps those coordinates to a fixed SVG viewBox. The trail samples the same evaluator at earlier days. Viewport changes scale the SVG uniformly without changing geometry or time.

`web/src/chronology.ts` implements Egyptian 365-day dates and proleptic Julian civil labels with astronomical year numbering. Its time argument is the continuous Egyptian mean local day count from the Alexandria-noon epoch, not a JavaScript `Date` or a TT/UT timestamp. `web/src/state.ts` contains pure control transitions; `web/src/i18n.ts` is the complete English/Mongolian catalogue; `web/src/app.ts` binds controls and renders. Playback advances the same day argument used by Python. Hiding the page pauses it.

`scripts/generate_mars_cross_language.py` writes Python results for historical examples, the Neugebauer reconstruction inputs, synthetic arguments, and continuous dates to `tests/fixtures/mars-cross-language.json`. Both Python and TypeScript tests check this file. The browser defaults to the Nabonassar example recorded in `mars-source-cases.json`; its exact time-evaluated longitude is `47.660458°`, while the exact geometry at P2's rounded arguments is `47.660439°`.

Vite's root is `web/`, its base is `/epicycle/`, its public directory is disabled, and the build emits only that import graph to `dist/`. The local information panel names the model's partial validation and distinguishes direct geometry from Ptolemy's table interpolation. Later comparison panels should reuse the evaluator/render boundary rather than adding a second body or variant to this Phase 2 view.

## Comparison contract

Phase 3A established the concrete [comparison convention](comparison-conventions.md): geocentric ecliptic longitude is the first observable; a sample carries physical-instant, frame, body, observer, and position-kind metadata; residuals require matched metadata and wrap on `[-180°, 180°)`. The Python chronology boundary explicitly converts an assumed UT1 JD to a sourced local mean meridian and, separately, to TT under a stated ΔT assumption. Neither the historical Egyptian day count nor a modern TDB is inferred from an unlabelled JD. Latitude and distance remain outside the first comparison.

The first Copernican Mars result depends on one source-checked, compatible Earth annual-motion version plus the Mars motion. Keep version, body, supported observable, epoch, frame, units, and source locators with both records; reject version mismatches when composition is implemented. The Phase 3B implementation below uses an explicit Earth dependency, without a general dependency framework. The source-reading scope is C1 III.1–26 and V.1–4, 15–19, 33–34, checked against C3 chs.3 and 5 as specified in the convention document.

## Open decisions

The micro-VSOP term threshold in CALTIB is a size heuristic (`|A|·3^power`), not a global error guarantee. Before choosing browser coefficients, benchmark longitude, latitude, and distance over declared historical epochs against an appropriate local high-precision ephemeris, including near close approaches and range boundaries. Verify the generator's source files, checksums, licenses, coefficients, and coordinate convention. Evaluate light-time and apparent-place needs separately. For Python, verify actual kernel coverage and the ancient ΔT model before claiming a historical error figure.


## Phase 3B scientific implementation

- `copernicus_earth.py` evaluates the 1543 double eccentric in true-Sun coordinates, plus the historical longitude component of precession. Direct arguments and continuous days are separate entry points. Its annual-circle centre G is the planetary mean Sun.
- `copernicus_mars.py` checks the specific Earth record identity/schema, epoch and frame, then scales its geometry by 6580/10000 and composes Mars's eccentric and small epicycle. The result separates original Earth geometry, scaled Earth geometry, Mars construction, Earth-to-Mars vector, corrections and sidereal/tropical geocentric longitudes. Proper mean motion derives from Earth mean solar motion minus commutation.
- The two versioned Copernican JSON records preserve adopted parameters, discarded variants and explicit nulls for missing secular laws. A caller must supply an apsis with provenance or select the limited scholarly reconstruction. Direct argument evaluation does not imply a time law.
- `copernicus_diagnostic.py` joins the existing Ptolemaic evaluator to the Copernican pair at one tagged UT1 instant. Meridian choices and any planar frame alignment are explicit. It uses the existing `LongitudeSample` guard after alignment; there is no modern reference adapter.
- `tests/fixtures/copernicus-source-cases.json` contains historical transcriptions. The scientific tests compare circle/vector invariants and independent scalar equations, original parameter derivations and scholarly table results. It is deliberately separate from the generated Phase 2 cross-language fixture.

See [the mathematical specification](copernicus-earth-mars.md) for formula signs, coordinates, policy domain, measured discrepancies and commands. Phase 3C subsequently added a TypeScript port on its review branch.

## Phase 3C browser comparison branch

The review-pending branch adds `web/src/copernicus.ts`, a pure TypeScript port of the accepted Earth and coupled Mars evaluators using the same versioned JSON records. `web/src/comparison-time.ts` maps a labelled Julian Frauenburg local mean date through one assumed UT1 JD into separate Frauenburg and Alexandria historical day arguments. `web/src/comparison.ts` produces native results and a conditional nominal-frame residual, and samples a two-curve time series with whole-turn unwrapping. The source-controlled `copernicus-cross-language.json` fixture is generated by Python and checked in both test suites.

`web/src/model-registry.ts` lists the two implemented, versioned Mars definitions with source, observable, dependency, and date-policy metadata. Single mode selects either model; comparison mode independently selects A and B. `web/src/state.ts` retains one `playing` flag and one animation loop. It stores the accepted Ptolemaic single-view Nabonassar day and the selected-model UT1 instant separately. `app.ts` renders only the active view. Static controls update on actions; animation frames update time, readouts, geometry, and the plot marker. Plot curves have an independent fixed date range and a cache key that excludes playback time. `copernicus-diagram.ts` translates evaluated original points by evaluated Earth position for geocentric display; its scale is fixed within the panel and differs from the Ptolemaic scale.

The versioned Mars record distinguishes the guarded `sn-local-uniform-1473-1523` scholarly reconstruction from `sn-uniform-exploratory`, a hypothetical continuation of its uniform rate and fixed 1543 geometry. The latter is never selected silently; the interface warns persistently when active. The guard is a project source boundary, not a mathematical or certified accuracy limit. The wider JD 1,200,000–3,000,000 interaction limit and 50-year plot span are numerical safety limits only. A caller-supplied apogee with provenance remains available in Python. The Today control alone reads the modern UTC clock, treats it approximately as UT1, then labels the resulting Frauenburg local date in the proleptic Julian calendar. Ordinary historical dates, including BCE dates, use numerical Julian chronology without JavaScript `Date`.

This branch has no modern reference adapter, no source-backed Alexandria meridian, and no original general Copernican Mars apsidal law. The nominal frame identification is declared in the interface and cannot be used as a calibrated error measure. The deployed Pages workflow remains untouched.
